# polish-learning

Matt's Polish vocabulary system. Two SQLite databases, split by who owns the fact.

| file | owns | size | precious? |
| --- | --- | --- | --- |
| `polish.db` | what Matt knows | ~10 KB | yes, but rebuilt from `db/forms.tsv` |
| `dict.db` | all Polish linguistic facts | 147 MB | no, rebuilt from the Wiktionary dump |

Neither `.db` file is the source of truth. The text files in `db/` are. Both databases are
generated by `make` and can be deleted at any time.

## Hard rules

1. **Never add a word to `db/forms.tsv` that Matt has not said he knows.**
   Not inflected forms he hasn't met, not obvious paradigm gaps, not function
   words he clearly needs. If a word would be useful to him, say so in chat and
   let him decide. This rule has been broken once; do not break it again.
2. **Only the agent writes. The reader only reads.** `reader/` opens SQLite,
   runs one SELECT, closes. Never add a write path to it.
3. **Never run `git add`, `git commit`, or `git push`** without Matt approving
   that exact action in the current message. Print the command instead.

## Soft rules for writing rows

These are not enforced by SQLite. `db/validate.py` warns about violations, and
the warnings are advisory only; a build never fails because of them.

4. **A dialogue must make sense before anything else.** It is a real exchange
   a person could actually have: the reply answers the question, the next turn
   follows from the last, and nobody says something a human never would.
   Prefer forms already in `known_forms`, but never at the cost of coherence.
   A stilted non-sequitur teaches nothing, so an easy new word is the right
   trade. This is not permission to add that word to `db/forms.tsv`, hard rule
   1 still holds. These dialogues were once written known-words-only and the
   result was nonsense like answering "Jak się masz?" with "Mam wodę."; do not
   regress to that.
5. **A dialogue gives context on both sides.** At least one turn before the
   phrase and one after, so Matt sees what prompts it and what answers it.
   Speaker labels are bare uppercase names followed by a colon (`JA:`, `MAYA:`).
6. **Do not guess `confidence`.** New rows default to 2. Matt sets 1 and 3.

## When you edit the vocabulary files

Run `make` afterwards. It validates, then rebuilds `polish.db`. Read the
validator's warnings, report them to Matt in chat, and recommend a fix for each
one. Do not silently fix a warning by adding words, that violates rule 1.

## Layout

```
db/forms.tsv       known forms, one per row, hand-edited as a grid
db/notes.tsv       per-lemma notes
db/phrases.md      phrases with their dialogues
db/build.py        parses the three files above into polish.db
db/schema.sql      3 tables: known_forms, lemma_notes, phrases
db/validate.py     soft checks, warnings to stderr, always exits 0
tokens.py          shared Polish word tokenizer
reader/            read-only highlighter, ANSI or standalone HTML
dictionary/         builds and queries dict.db from kaikki.org
```

## Style

Matt's global rules in `~/.claude/CLAUDE.md` apply. Shortest version:
correctness, then KISS, then DRY. No comments unless the code cannot explain
itself. No em-dashes in any prose. Run `ruff check --fix . && ruff format .`
after every Python change.
